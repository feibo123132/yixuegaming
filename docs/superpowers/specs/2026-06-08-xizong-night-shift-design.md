# 西综夜班：心血管竖切 Demo 设计规格

日期：2026-06-08  
阶段：第一版正式规格  
项目代号：西综夜班  
MVP 名称：胸痛夜班：STEMI 复诊链

## 1. 产品定位

本项目不是把西综题库换一层皮，而是做一款“真的好玩的医学策略游戏”。玩家表面上在值急诊夜班、处理胸痛病人、打出检查和治疗卡牌；底层实际反复训练西综中内科、外科、生理、生化、病理的高频知识点。

第一阶段聚焦心血管系统，做一个可被医学生内测的 Web 竖切 Demo。目标体验时长为 5-10 分钟，用户完成后应该能明确感到：这不是刷题软件，但确实帮我把一个考试知识链条玩了一遍。

核心设计原则：

- 先好玩，再承载知识。
- 医学内容必须可靠，AI 只做转译和生成辅助，最终由医学团队审核。
- 真题只进入后台拆解流程，不在玩家侧直接复现原题。
- 第一版不追求大而全，追求一个病种链条玩得通、讲得清、能复盘。

## 2. 目标用户与成功标准

首批目标用户是准备西综的临床医学本科生，尤其是已经接触过心血管基础知识、但对知识迁移和病例串联感到吃力的学生。

内测成功标准：

- 玩家不看说明也能在 1 分钟内理解基本操作。
- 玩家能在第一局中完成一次“胸痛病人接诊-检查-诊断-治疗-结算”的完整循环。
- 玩家在结算页能看懂自己错在哪里，并愿意再玩一局修正策略。
- 玩家能感受到知识点来自西综，而不是泛泛的医学科普。
- 医学内容团队能把 5 道真题稳定转译为 1 个主病例和 4 个变体。

## 3. 平台与范围

第一阶段平台选择 Web。原因是团队可以最快做出可分享、可测试、可迭代的 vertical slice，不被小程序审核、App 打包或 PC 客户端分发拖慢。

本规格只覆盖第一章心血管系统中的 STEMI 复诊链。暂不覆盖完整账号系统、付费系统、全科目题库、多人玩法、复杂养成、排行榜和正式发布运营。

第一版必须包含：

- 章节封面和进入夜班的过场。
- 单病例教学战斗。
- STEMI 主病例。
- 至少 4 个 follow-up 变体。
- 20 张以内的核心卡牌池。
- 战斗结算和知识复盘页。
- 一个轻量医院成长页或章节地图页。

## 4. 核心玩法循环

### 4.1 单局循环

单局由一名胸痛病人开始。玩家看到主诉、生命体征、初始病情和可用行动卡牌。玩家每回合使用有限资源执行检查、诊断或治疗。系统根据玩家操作推进疾病状态。

基本循环：

1. 病人进入急诊夜班。
2. 玩家读取病历摘要和生命体征。
3. 玩家从手牌中选择检查、诊断、治疗或机制类行动。
4. 系统更新检查结果、病情进展、风险值和资源消耗。
5. 玩家形成诊断并执行关键治疗。
6. 病例进入稳定、恶化、误治或失败结局。
7. 结算页显示医学解释、考试知识点和本局失误。

### 4.2 复诊链循环

同一个核心知识链在不同变体中反复出现，但表现形式变化。玩家第一次可能只学会“STEMI 要看 ECG”，后续会遇到肌钙蛋白早期阴性、主动脉夹层鉴别、右室梗死禁用硝酸酯、再灌注后并发症等变化。

复诊链目标是让玩家形成迁移能力，而不是背单一答案。

第一链条建议：

- Level 1：典型 STEMI。
- Level 2：早期肌钙蛋白阴性，强调时间窗。
- Level 3：胸痛鉴别诊断，警惕主动脉夹层和肺栓塞。
- Level 4：低血压或右室梗死场景，硝酸酯成为陷阱。
- Level 5：再灌注后并发症，如心律失常、心衰或休克风险。

## 5. 战斗界面

第一版战斗界面采用“急诊工作站 + 策略卡牌”的组合。

推荐布局：

- 左侧：夜班队列和当前患者列表。
- 中央：当前患者、病历摘要、检查报告和关键视觉反馈。
- 右上：生命体征、病情风险、时间推进、资源余量。
- 右侧：医嘱/行动记录。
- 底部：玩家手牌。
- 弹层：检查结果、诊断确认、治疗风险提示。

UI 气质应该像一个更好玩的急诊工作站，而不是传统问答页。玩家的注意力应集中在“病人正在变化”与“我下一张牌打什么”之间。

第一版不需要做真实 HIS，也不需要模拟所有医嘱细节。界面必须服务于策略判断：什么时候查 ECG，什么时候看肌钙蛋白，什么时候抗血小板，什么时候不能用硝酸酯，什么时候必须排除夹层。

## 6. 卡牌系统

### 6.1 卡牌类型

卡牌分为六类：

- 检查卡：获得信息，例如 ECG、肌钙蛋白、超声、D-二聚体、CTA。
- 治疗卡：改变病情，例如阿司匹林、P2Y12、肝素、硝酸甘油、氧疗、升压支持、PCI。
- 诊断卡：提交或锁定判断，例如 STEMI、NSTEMI、主动脉夹层、肺栓塞。
- 机制卡：解释或强化理解，例如冠脉闭塞、心肌缺血坏死、标志物时间窗、右室梗死。
- 资源卡：恢复或调整行动资源，例如补充夜班精力、加急检验、请上级会诊。
- 陷阱/状态卡：由病情或错误操作触发，例如低血压、延误再灌注、出血风险、误用硝酸酯。

### 6.2 第一版核心卡牌池

建议第一版控制在 20 张以内：

- ECG。
- 肌钙蛋白。
- 超声心动图。
- D-二聚体。
- CTA。
- 阿司匹林。
- P2Y12 受体拮抗剂。
- 肝素。
- 硝酸甘油。
- 氧疗。
- 循环支持。
- 急诊 PCI。
- STEMI。
- NSTEMI。
- 主动脉夹层。
- 肺栓塞。
- 冠脉闭塞。
- 心肌缺血坏死。
- 生物标志物时间窗。
- 右室梗死。

卡牌文本分两层。战斗中只显示短句和关键词，避免像教材；结算页展开考试解释、错误原因和对应知识点。

## 7. 内容数据结构

内容后台需要把“真题”转译成游戏可用的结构化内容。

主要实体：

- SourceQuestion：原始真题，仅后台使用。
- ExamPoint：考试知识点，例如 STEMI 诊断依据、肌钙蛋白时间窗、右室梗死禁忌。
- Mechanism：机制解释，例如冠脉急性闭塞导致透壁性心肌缺血。
- ActionCard：玩家可使用的检查、治疗、诊断或机制卡。
- Case：可游玩的病例。
- Variant：同一知识链的变体病例。
- Outcome：结局与评分。
- Debrief：结算页知识复盘。

### 7.1 真题转译流程

推荐流程：

1. 医学团队导入 5 道真题。
2. AI 初步拆解题干、选项、考点、陷阱、机制和错误原因。
3. 医学团队审核并修正拆解结果。
4. 系统把考点映射到卡牌、病情状态和病例节点。
5. 生成 1 个主病例和 4 个变体病例。
6. 医学团队进行可玩性与医学正确性双审。
7. 内测用户游玩后收集行为数据和错因反馈。

### 7.2 版权与合规原则

真题只能作为内部知识拆解材料。玩家侧不展示原题题干、原题选项或原题解析。玩家看到的是原创病例、原创卡牌、原创解释和原创交互。

如果后续需要商业化，应进一步确认真题来源授权、用户数据合规、医学教育免责声明和 AI 生成内容审核记录。

## 8. 状态与评分

病例状态建议包括：

- 病情稳定度。
- 缺血进展。
- 再灌注倒计时。
- 误诊风险。
- 出血风险。
- 血流动力学状态。
- 玩家资源，例如行动点、时间、夜班精力。

结局分级建议：

- S：快速识别，关键检查和治疗路径优秀，复盘中只提示优化。
- A：正确诊治，有少量资源浪费。
- B：最终正确，但延误关键步骤。
- C：诊断方向摇摆，治疗不完整。
- D：误治或漏掉关键禁忌，病情明显恶化。
- F：严重误诊、关键治疗失败或触发致命风险。

评分不应只服务于惩罚，而要服务于复盘。玩家应知道“为什么扣分”和“下一局怎么变好”。

## 9. 视觉风格

已确定风格为“临床夜班策略风”。

风格关键词：

- 半写实急诊医学场景。
- 战术化医疗 HUD。
- 可收藏但可读的策略卡牌。
- 克制的危险色，而不是恐怖或血腥表现。
- 深色夜班基底，冷白医疗光，ECG 绿，青色信息光，红橙色风险提示。

需要避免：

- 纯题库软件感。
- 过度写实导致像医院培训系统。
- 过度赛博朋克导致医学可信度下降。
- Q 版低龄化。
- 恐怖、血腥或猎奇化患者表现。

## 11. 技术设计建议

第一版可以拆为五个前端/内容模块：

- GameShell：章节入口、战斗页、结算页、医院成长页的路由外壳。
- BattleEngine：病例状态机、行动点、时间推进、结局判定。
- CardSystem：卡牌定义、手牌、出牌合法性、卡牌效果。
- CaseContent：病例 JSON、变体 JSON、检查结果、结算解释。
- VisualLayer：背景图、患者状态图、HUD、卡牌视觉和动效。

数据先使用本地 JSON 即可，不急于引入复杂后端。只有当真题导入、内容审核、多人协作编辑成为主要瓶颈时，再建设内容管理后台。

推荐第一版数据边界：

- 程序团队负责状态机和 UI 渲染。
- 医学内容团队负责病例 JSON 的医学正确性。
- UI 团队负责界面组件和信息层级。
- 产图团队负责背景、卡面、患者状态和图标资产。

## 12. 数据流与异常处理

### 12.1 基础数据流

第一版推荐使用本地静态内容驱动：

1. 页面加载章节配置。
2. 章节配置加载病例 JSON 和卡牌 JSON。
3. BattleEngine 初始化患者状态、玩家资源和起始手牌。
4. 玩家出牌后，CardSystem 校验出牌条件。
5. BattleEngine 应用卡牌效果并推进病例状态。
6. VisualLayer 根据状态变化更新患者图、HUD、报告和行动日志。
7. 病例结束后，Outcome 与 Debrief 生成结算结果。

这条链路必须保持可追踪：每一次关键出牌都应该能在行动日志中复现，方便医学团队和程序团队定位“是内容配置错了，还是引擎判定错了”。

### 12.2 异常处理

第一版至少需要处理以下异常：

- 缺失卡牌定义：界面显示占位卡，控制台输出具体 cardId。
- 缺失病例节点：战斗中断并进入错误结算页，提示内容配置需要修复。
- 非法出牌：不消耗行动点，给出简短反馈，例如“当前血压状态下不建议使用”。
- 医学高风险操作：允许玩家犯错，但必须明确触发风险与复盘解释。
- 资源不足：按钮置灰或卡牌不可打出，避免玩家误以为系统卡住。
- 图片加载失败：使用纯色面板和图标占位，不影响核心玩法。

医学内容异常不能静默吞掉。凡是影响诊断、治疗、禁忌或结算解释的配置缺失，都应在开发环境中显式报错。

## 13. 测试与验证

第一版测试重点：

- 卡牌效果是否正确改变病例状态。
- 关键医学路径是否符合共识：疑似 STEMI 优先 ECG、再灌注治疗不能被无意义步骤拖延、低血压/右室梗死场景下硝酸酯风险明确。
- 结算页是否能解释玩家的错误。
- UI 是否在桌面和常见笔记本分辨率下可读。
- 玩家是否能在无指导下完成第一局。

医学审核建议采用双人审核：一名负责考试知识点，一名负责临床合理性。争议点记录到内容审查表，不在代码里口头解决。

## 14. 第一版里程碑

建议里程碑：

1. 规格确认：确认本文档范围和第一版 STEMI 链条。
2. 内容样例：用 5 道真题生成 1 个主病例和 4 个变体的结构化草稿。
3. UI 原型：完成战斗页、结算页、医院地图页静态原型。
4. 引擎接入：完成卡牌出牌、状态推进、结局判定。
5. 美术替换：将第一批关键视觉资产接入界面。
6. 内测版本：邀请 5-10 名医学生完成首轮测试。
7. 复盘迭代：根据错因、停留时间、重玩意愿修正病例和交互。

## 15. 暂不做事项

第一版暂不做：

- 完整五大学科内容。
- 大规模题库导入。
- 复杂抽卡和商业化数值。
- 多角色养成。
- 真实医院流程模拟。
- 用户账号、云存档和付费系统。
- 对外公开发布。

这些不是不重要，而是会稀释第一版目标。第一版的任务只有一个：证明“西综知识可以被做成真正好玩的病例卡牌策略循环”。

## 16. 待确认问题

进入代码设计前，需要团队确认：

- 第一版是否只做桌面 Web，还是同时适配手机竖屏。
- 5 道 STEMI 相关真题的具体文本和来源格式。
- 医学内容审核负责人是谁。
- UI 团队是否采用现有设计系统，还是从本项目新建组件规范。
- 第一版是否需要记录用户行为数据；如果需要，记录本地日志还是接入后端。
